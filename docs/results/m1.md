## Analyze and improve

- The first full run of the audit found `pip 26.1.1` in the virtual environment with two
  advisories (PYSEC-2026-196, PYSEC-2026-3721); `make setup` and `.tmp/check.sh` now upgrade pip
  first, and the audit is clean.
- A first version of the demo test indexed scenarios by caller name and two scenarios share the
  caller `frontend`; the test now indexes by position.
- `mypy --strict` flagged that spec values reach `validate_label` untyped; the validator now
  takes `object` and checks the type itself.
- The register script failed on a second run in principle (`entry create` on an existing entry);
  it now treats "already exists" as success, and the kind job runs it twice.

## First kind run (2026-11-16)

Run 43901407697: `build` and `envoy-validate` passed; `kind-e2e` failed in "End-to-end check"
with `frontend never reached backend: HTTP/1.1 503 Service Unavailable`.

- The spire-agent annotation showed `workload is not authorized for the requested identities`
  for frontend, backend and intruder between 15:55:43 and 15:55:46, then `Creating X509-SVID`
  for frontend and backend at 15:55:47. After that only the intruder (no entry, as intended)
  kept being refused. The SPIRE side worked: attestation matched the `k8s:ns`/`k8s:sa`
  selectors under the node alias, and the early refusals came from the agent minting SVIDs
  only once a matching workload asked; Envoy retried the SDS stream and got them. The step
  still failed two minutes later, so the 503 was not an identity problem.
- Root cause: `tls_params` set only `tls_minimum_protocol_version: TLSv1_3`. Envoy's
  documented default maximum is `TLSv1_2` for clients (`TLSv1_3` for servers), so the frontend's
  upstream context had an empty version range (1.3 to 1.2) and every connection to the backend
  failed before HTTP. `envoy --mode validate` cannot catch this: the TLS context is built only
  when SDS delivers the certificate.
- Fix: `envoy.tls_context` sets `tls_maximum_protocol_version: TLSv1_3` too; the configs were
  re-rendered. `test_every_tls_context_pins_tls13_at_both_ends` fails when the maximum is
  removed (mutation run, then restored).
- Diagnosability: on failure `deploy/kind/e2e.sh` now writes `::error` annotations with
  `spire-server entry show` (IDs, parents, selectors), `agent list` and `agent show` (the
  agent's node selectors), the frontend's full 503 response (Envoy puts the transport failure
  reason in the body), TLS/SDS lines from both Envoy logs, and the agent log without the
  expected intruder refusals. After registration it prints the entries as a `::notice`.

## Security review fixes (2026-11-10)

An automated security review raised two findings, both fixed with a regression test that fails
when the fix is reverted:

- `files.write_atomic` used a predictable temp name opened without `O_EXCL`, so a planted file or
  symlink could be reused. It now uses `tempfile.mkstemp` in the target directory (`O_EXCL`,
  random name, owner-only) and then applies the requested mode.
- The Envoy admin API listened on 127.0.0.1:9901, reachable without authentication from the app
  container in the same pod. It now listens on a Unix socket (`/var/run/envoy-admin/admin.sock`,
  mode 0600) in a memory `emptyDir` mounted only into the envoy container. The kind check that read
  the SVID expiry from admin `/certs` now reads it from the backend's
  `x-peer-cert-not-after: %DOWNSTREAM_PEER_CERT_V_END%` response header, and a new kind step checks
  the app container cannot reach admin.
